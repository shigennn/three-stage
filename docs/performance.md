# 性能

このドキュメントでは、シーンを目標のフレームレートとメモリの上限に収めるための、設計上の目標、計測方法、最適化の考え方、ポストプロセスの負荷を説明する。\
Stats と Profiler の画面は [studio.md](studio.md)、計測コマンドの引数は [packages/studio/tools/README.md](../packages/studio/tools/README.md) を参照。

## 概要

以下、シーンを組み込む Web アプリケーションを「組み込み先」と呼ぶ。\
エディタと組み込み先は、同じランタイム（`@three-stage/runtime`）で描画する。\
描画には WebGL2（three.js の WebGLRenderer）を使用し、React Three Fiber 上で動作する。\
そのため、エディタと `preview.html` で計測した値は、同じ条件であれば組み込み先でも同じになる。\
`preview.html` は、組み込み先と同じ描画のみを表示するページである。

性能は、次の手順で扱う。

1. 設計上の目標を確認する。\
   対象はフレームレート、対象とする PC、1 フレームの時間の上限、メモリの上限である。
2. 作成中は、エディタの Stats と Profiler で値を確認する。
3. `three-stage measure` と `three-stage soak` で、条件を揃えて計測する。
4. 上限を超えた場合は、「最適化の考え方」に沿って負荷を減らす。

## 設計上の目標

この章の値は、THREE Stage の設計上の目標である。\
Stats と Profiler の警告表示と上限の線、`three-stage measure` の比較、`three-stage soak` の判定は、この目標を基準にする。\
組み込み先の PC と表示条件が異なる場合は、その PC で計測して判断する。

### フレームレート

フレームレートの目標は 30 fps である。\
60 fps は目標にしない。\
性能の計測と上限の値は、30 fps を前提とする。

ランタイムは、requestAnimationFrame（rAF）のたびに前回の描画からの経過時間を確認し、25 ms 未満であれば描画を省略する。\
60 Hz のモニターでは 2 回に 1 回描画するため、フレームの間隔は 33.3 ms で一定になる。\
60 Hz 以外のモニターでは、間隔は一定にならない。

30 fps の制限は、次の場所で切り替える。

| 場所 | 設定 | 既定値 |
|---|---|---|
| エディタ | Viewport 上部の Render の Frame Rate | `30 fps` |
| `preview.html` | クエリの `limit=0` で制限を解除 | 制限あり |
| 組み込み先 | `StageView` の `settings.limitFps` | `true` |

エディタの Frame Rate は、`30 fps` または `Unlimited` を選択する。

### 対象とする PC

対象とする PC は、内蔵 GPU の性能で区分する。

| 区分 | GPU | メモリ | 描画解像度 | 目標 |
|---|---|---|---|---|
| 推奨 | UHD 730 以上、または Core Ultra の内蔵 GPU | 16 GB（8 GB × 2 のデュアルチャネル） | 1080p | 30 fps |
| 最低 | UHD 620/630、または N100/N150 | 8 GB 以上 | 720p まで低下 | 30 fps |
| 対象外 | ブラウザが GPU を使用できない環境 | — | — | — |

推奨の区分は、一般的なデスクトップ PC の内蔵 GPU を想定する。\
該当するのは Core i5 第 12〜14 世代（UHD 730 以上）と Core Ultra である。\
1080p で描画し、4K モニターにはアップスケールして表示する。

最低の区分は、Windows 11 が動作する PC を想定する。\
該当するのは Core 第 8〜11 世代の UHD 620/630 と、N100/N150 のミニ PC である。\
Dynamic Resolution で描画解像度を 720p まで下げる。

型番の末尾に F が付く Core（i5-12400F など）は内蔵 GPU を持たないため、対象外の区分になる。

推奨の区分は UHD 730 を基準にする。\
デスクトップ PC で一般的な i5-12400／13400／14400 の内蔵 GPU は UHD 730（24 EU）である。\
UHD 770（32 EU）を搭載するのは i5-12500 以上である。

Dynamic Resolution は、描画解像度の設定（Resolution）が `auto` の場合のみ動作する。\
Resolution の既定値は `1080p` である。\
最低の区分の PC を対象にする場合は、組み込み先で `StageView` の `settings.resolution` を `auto` に設定する。\
解像度を下げる条件は、「GPU」の「Dynamic Resolution」を参照。

2D UI は HTML であり、画面の解像度のまま描画される。\
4K モニターでは 4K で描画される。

### 1 フレームの上限

基準とする PC は Core i5-1235U（Intel Iris Xe 80 EU、最大 1.2 GHz）である。\
対象とする PC での時間は、内蔵 GPU の性能を基準の Iris Xe との比で見積もり、基準の PC での 1 フレームの時間に換算する。

| GPU | EU 数 × 最大クロック | 性能比 |
|---|---|---|
| Iris Xe（i5-1235U、基準） | 80 × 1.2 GHz | 1 |
| UHD 770（i5-12500 以上） | 32 × 1.45 GHz | 0.48 |
| UHD 730（i5-12400／13400／14400） | 24 × 1.45 GHz | 0.36 |
| UHD 620/630 | 24 × 1.0〜1.2 GHz | 0.25〜0.30 |
| N150 | 24 × 1.0 GHz | 0.25 |
| N100 | 24 × 0.75 GHz | 0.19 |

性能比は、公称の EU 数とクロックから算出した理論値であり、実測値ではない。\
メモリ帯域を考慮していないため、画素数がボトルネックになる場面では、実際の比と異なる場合がある。\
Core Ultra は型番によって内蔵 GPU の構成が大きく異なるため、この表には含めない。

| 区分 | 対象とする PC での目標 | 計算 | 基準の PC での上限 |
|---|---|---|---|
| 推奨 | UHD 730 で 1080p、30 fps（33.3 ms） | 33.3 × 0.36 | 1080p で 12 ms |
| 最低 | N100 で 720p、30 fps（33.3 ms） | 33.3 × 0.19 | 720p で 6 ms |

この上限と比較するのは、30 fps の制限を解除して計測したフレームの間隔である。\
Stats と Profiler は、描画バッファの高さが 760 px 以下であれば 6 ms、それより大きければ 12 ms を上限とする。\
`three-stage measure` では、出力の `frameMs`（フレームの間隔の中央値）を比較する。

### メモリの上限

内蔵 GPU は、メインメモリを共有する。\
Intel は、Iris Xe の性能を発揮するにはデュアルチャネルのメモリが必要であるとしている。\
メモリが 1 枚のみの場合、Iris Xe は UHD と同等の性能で動作する。

| 項目 | 上限 |
|---|---|
| GPU 上のテクスチャ | 256 MB |
| タブ全体 | 1 GB |
| 長時間の動作 | 使用量が増加し続けないこと |

Stats と Profiler は、JS のヒープが 1024 MB を超えると警告色で表示する。\
テクスチャは枚数（Textures）のみが表示されるため、使用量は「GC とメモリ」の計算式で見積もる。\
使用量が増加し続けないことは、`three-stage soak` で確認する。

## 計測方法

### Stats と Profiler

エディタでは、作成中に次の 2 か所で値を確認できる。\
画面と項目の詳細は [studio.md の「Stats と Profiler」](studio.md#stats-と-profiler) を参照。

| 場所 | 表示内容 |
|---|---|
| Stats（Viewport の右上） | 直近の各指標の値 |
| Profiler（下部のタブ） | 各指標の直近 60 秒のグラフ |

Stats には、fps、フレーム時間、CPU と GPU の時間、Calls、Triangles、Geometries、Textures、JS Heap、GC Alloc が表示される。\
上限を超えた値は、警告色で表示される。\
Profiler の Frame Time と CPU・GPU のグラフには、上限の線が表示される。\
Frame Time のグラフには、33.3 ms の線も表示される。

30 fps の制限が有効な場合、フレームの間隔は 33.3 ms で一定になり、負荷の大きさを確認できない。\
負荷を確認する場合は、Render の Frame Rate を `Unlimited` に設定する。\
Stats がフレーム時間を警告色で表示するのは、`Unlimited` の場合のみである。

### 計測コマンド

条件を揃えて計測する場合は、次の 3 つのコマンドを使用する。\
いずれも、`three-stage <フォルダ> --no-open --port 5180` で起動したエディタのサーバーのページを、ヘッドレス Chrome で開く。\
計測の対象は `http://127.0.0.1:5180/preview.html` である。

| コマンド | 内容 |
|---|---|
| `three-stage shot <steps.json> <出力フォルダ>` | 1920 × 1080 のスクリーンショットの撮影と、2D UI の文字の重なりとはみ出しの検出 |
| `three-stage measure <URL または runs.json>` | 1 フレームの draw call、ポリゴン数、パスごとの内訳、フレームの間隔の計測 |
| `three-stage soak <URL> --minutes <分>` | JS のヒープと WebGL のオブジェクト数が増加し続けないかの判定 |

`shot` は表示内容の確認に使用し、速度は計測できない。

1 フレームの上限と比較する場合は、30 fps の制限を解除して計測する。

```powershell
three-stage measure "http://127.0.0.1:5180/preview.html?limit=0"
```

長時間の安定性は、モックデータの時刻を早送りして確認する。\
`speed=1440` を指定すると、モックデータの 1 日が 1 分で進む。

```powershell
three-stage soak "http://127.0.0.1:5180/preview.html?start=00:00&speed=1440&limit=0" --minutes 30
```

引数、`preview.html` のクエリ、出力の項目は [packages/studio/tools/README.md](../packages/studio/tools/README.md) を参照。

CPU の内訳は、Chrome の DevTools の Performance で確認する。\
1 フレームのうち、Scripting と Rendering が占める時間を確認する。

## 最適化の考え方

最適化は、次の 4 つの観点で行う。

1. 毎フレームの CPU の処理を減らす。
2. 長時間の動作で増加し続けるものをなくす。
3. GPU が描画する画素を減らす。
4. 2D UI の負荷を低く保つ。

内蔵 GPU では、ポリゴン数より画素数のほうが負荷に影響することが多い。\
ブラウザでは CPU と GPU の使用率を直接指定できない。\
そのため、1 秒あたりの描画回数と、1 回あたりの処理量で調整する。

### CPU

| 手法 | 効果 |
|---|---|
| フレームレートの制限 | 30 fps にすると、CPU と GPU の処理がおおよそ半分になる |
| データ受信時の一括計算 | 毎フレームの計算が補間のみになる |
| シェーダーによるアニメーション | 頂点ごとの計算が GPU で行われる |
| 静的なオブジェクトの行列の固定 | 行列の再計算が省略される |
| 変更部分のみの転送 | GPU へのデータ転送量が減る |
| オブジェクトの再利用 | 切り替え時の生成とシェーダーのコンパイルが発生しない |

各手法の方法は次のとおりである。

- データの更新間隔は、フレームの間隔よりはるかに長い。\
  並べ替えや配分はデータの受信時に一度だけ計算し、毎フレームは補間のみを行う。
- 流れや点滅は、`uTime` などの uniform を 1 つ渡し、頂点ごとの動きを GPU で計算する。
- 静的なオブジェクトには、`matrixAutoUpdate = false` を設定する。
- `needsUpdate` は値が変更されたときのみ `true` にし、バッファは `addUpdateRange` で変更範囲のみを転送する。
- 切り替えて表示するオブジェクトは保持したまま、表示と非表示のみを切り替える。\
  シェーダーは、最初に `renderer.compileAsync` でコンパイルしておく。

### スレッド

JavaScript のメインスレッドは 1 本である。\
JS の実行、DOM の更新、three.js による描画コマンドの生成は、すべてメインスレッドで行われる。\
GPU の処理は Chrome が別のプロセスで実行するため、描画のためにスレッドを分ける必要はない。

| 手段 | 用途 | ランタイムでの使用 |
|---|---|---|
| Web Worker | 重い計算を別スレッドで実行する | Draco と KTX2 のデコードで使用 |
| OffscreenCanvas | three.js の描画を Worker に移す | 使用しない |
| SharedArrayBuffer | スレッド間でメモリを共有する | 使用しない |

Draco で圧縮した glb と KTX2 テクスチャのデコードは、three.js のローダーが Worker で行う。\
コンポーネントの重い計算は、Worker に移すことができる。\
ランタイムは、メインスレッドで描画する。

SharedArrayBuffer を使用するには、組み込み先のページに COOP と COEP のヘッダーが必要である。\
ランタイムは SharedArrayBuffer を使用しないため、組み込み先でこれらのヘッダーを設定する必要はない。

### GC とメモリ

GC（ガベージコレクション）は、参照されなくなったオブジェクトをブラウザが自動で解放する仕組みである。\
解放の間は JS の実行が停止するため、毎フレームオブジェクトを生成すると、フレームの遅延が発生する。\
GPU 上のデータは GC の対象外であり、`dispose()` で明示的に解放する。

| 対象 | 問題 | 対策 |
|---|---|---|
| JS の一時オブジェクト | 毎フレームの `new Vector3()`、配列、文字列が GC を発生させる | 一時変数を再利用する |
| 文字列の更新 | 数値の整形で、毎フレーム文字列が生成される | 表示内容が変更されたときのみ更新する |
| GPU のメモリ | ジオメトリ、マテリアル、テクスチャ、レンダーターゲットが残る | 不要になったら `dispose()` を呼び出す |
| 増加する配列 | ログや時系列データが、長時間の動作で増加する | 長さを固定したリングバッファにする |
| DOM | 一覧に行を追加し続けると、削除されない要素が残る | 行を一定数だけ生成し、内容のみを入れ替える |

GPU のメモリが増加し続けていないかは、`renderer.info.memory` で確認する。

テクスチャ 1 枚のメモリ使用量は、幅 × 高さ × 4 バイト × 1.33 で見積もる。\
1.33 は、ミップマップの分である。\
KTX2 は GPU 上でも圧縮されたまま保持されるため、使用量が 4〜8 分の 1 になる。

GC Alloc（Stats と Profiler）は、GC と GC の間に JS のヒープが 1 秒あたりに増加した量である。\
毎フレームのオブジェクトの生成を減らすと、この値は下がる。

長時間の動作でメモリが増加し続けないかは、`three-stage soak` で確認する。\
手動で確認する場合は、DevTools でヒープスナップショットを時間を空けて 2 回取得し、比較する。

### GPU

| 手法 | 効果 |
|---|---|
| 描画解像度の抑制 | 最も効果が大きい |
| Dynamic Resolution | 遅い PC で描画解像度を自動で下げる |
| ポストプロセスの削減 | 全画面のパスが減る |
| シャドウの更新頻度の抑制 | シャドウマップの描画が減る |
| ライトの削減 | 画素ごとの計算が減る |
| オーバードローの削減 | 同じ画素を描画する回数が減る |
| 品質の段階の切り替え | 描画解像度の上限とシャドウマップの大きさが下がる |

ポストプロセスの負荷は、「ポストプロセスの負荷」を参照。

#### 描画解像度

3D は 1080p または 720p で描画し、2D UI のみを画面の解像度で描画する。\
ランタイムは、Resolution の設定と、Quality の Max Resolution のうち小さいほうの高さで描画する。\
画面の画素数より高い解像度では描画しない。

#### Dynamic Resolution

Resolution が `auto` の場合、ランタイムは 2 秒に 1 回、直近 60 フレームの間隔を判定する。\
Frame Time Threshold（既定値 40 ms）を超えたフレームが 12 フレームを超えると、描画解像度の高さを Minimum Resolution（既定値 720）に下げる。\
一度下げた解像度は戻さない。\
各値は Render Settings で変更する。

#### シャドウ

太陽のように光源がゆっくり移動する場合は、`shadowMap.autoUpdate = false` を設定し、1 分に 1 回などの間隔で更新する。\
影を落とすオブジェクトが移動したときは、その時点で `shadowMap.needsUpdate = true` を設定する。\
静的なオブジェクトの影は、モデリングツールでライトマップにベイクする。\
Quality の Shadow Map Scale で、シャドウマップの大きさを下げることができる。

#### 空の切り替え

Environment の HDRI と HDRI B を Blend で混合する場合、ランタイムは Blend を 64 段階に分割する。\
環境光（PMREM）は、段階が変化したときのみ再生成される。\
Blend が 0 と 1 の環境光は、一度生成すると保持される。\
そのため、再生成は Blend が中間の値を通過する間のみ発生する。

#### リフレクション

Reflection Probe は、毎フレームは再撮影しない。\
再撮影するのは、オブジェクトの追加と削除、シーン定義の変更、表示と非表示の変更、空の切り替えのときのみである。\
再撮影の間隔は、最短で 0.5 秒である。\
キューブマップの 6 面は、1 フレームに 1 面ずつ撮影する。\
影は、撮影時点のシャドウマップを使用する。\
移動し続けるオブジェクトは、再撮影されるまで反射に反映されない。

#### ライトとオーバードロー

ライトを増やすと、画素ごとの計算が増加する。\
エミッションとベイクで置き換え、ライトは 2〜3 個に抑える。

半透明の大きな板や、加算合成で重なる光は、同じ画素を何度も描画する。

#### 品質の段階

Quality の High と Low で、描画解像度の上限とシャドウマップの大きさを切り替える。\
組み込み先では、`StageView` の `settings.quality` で指定する。

`powerPreference` は、GPU を 2 つ搭載したノート PC でのみ効果がある。

### 2D UI

2D UI は HTML であり、画面の解像度のまま描画される。\
そのため、4K モニターでは描画する画素数が多くなる。

| 手法 | 方法 |
|---|---|
| アニメーション | `transform` と `opacity` のみを変化させる |
| 重い効果 | `backdrop-filter` のぼかしは、計測してから使用する |
| 描画範囲の限定 | パネルに `contain: layout paint` を設定する |

幅や位置を変化させると、レイアウトの再計算が発生する。\
`backdrop-filter` のぼかしは、4K では負荷が大きい。

### パーティクル

1. 粒を 1 つずつ Mesh にせず、`InstancedMesh` または `Points` にまとめ、draw call を 1 回にする。
2. 位置は「経路上の位置 = fract(粒ごとの乱数 + 位相)」のように頂点シェーダーで計算し、CPU は uniform を渡すのみにする。
3. データの値に比例して速度を変化させる場合は、CPU で `位相 += 速度 × 経過時間` を積算してから渡す。\
   時間に速度を直接掛けると、速度が変化した瞬間に粒の位置が飛ぶ。
4. 最大数を最初に確保し、表示する数は `mesh.count` または `setDrawRange` で変更する。
5. 粒は小さくして `depthWrite: false` を設定し、加算合成で重なる数に上限を設ける。\
   重なりすぎると、画面が白飛びする。
6. 線に沿った流れは、帯状のメッシュの UV をずらして表現すると、パーティクルより負荷が低い。

ランタイムは WebGL2 で描画するため、コンピュートシェーダーは使用できない。\
粒どうしの衝突判定のようなシミュレーションは、粒の数を抑え、CPU または頂点シェーダーで計算する。

## ポストプロセスの負荷

ランタイムのポストプロセスは、three.js の EffectComposer で構成する。\
シーンは半精度浮動小数点のレンダーターゲットに描画される。\
その後、Bloom、トーンマッピングと sRGB への変換、FXAA、SMAA の順に適用される。

プロジェクトで登録したポストエフェクトは、`stage` が `hdr` であれば Bloom の後、`display` であれば sRGB への変換の後に適用される。\
登録したポストエフェクトは、1 つごとに全画面のパスが 1 枚増える。\
Vignette はトーンマッピングのパスの中で適用されるため、全画面のパスは増えない。\
有効なエフェクトが 1 つもない場合は、EffectComposer を使用せず、キャンバスに直接描画する。

### 計測値

次の表は、2026-10-25 に基準の PC（Iris Xe、D3D11）で計測した `frameMs`（中央値）である。\
glb のモデルを十数個配置したシーンの `preview.html?limit=0` を、`three-stage measure` で計測した。

| ポストプロセス | 1080p | 720p |
|---|---|---|
| なし | 4.1 ms | 3.2 ms |
| Vignette | 5.6 ms | — |
| Bloom、Vignette | 8.5 ms | — |
| Bloom、Vignette、FXAA | 10.1 ms | 5.3 ms |
| Bloom、Vignette、SMAA | 14.0 ms | — |

SMAA を使用すると、1080p の上限 12 ms に収まらない。\
アンチエイリアスが必要な場合は、FXAA を使用する。

### アンチエイリアスと MSAA

ポストプロセスを使用すると、キャンバスの `antialias`（MSAA）は最後のパスにしか適用されない。\
そのため、オブジェクトの縁にジャギーが発生する。\
これを補うのが FXAA である。

ランタイムのレンダーターゲットは、MSAA を使用しない。\
同じ条件でレンダーターゲットに MSAA（`samples` が 2 または 4）を設定すると、中央値は変化しなかった。\
一方で、数フレームに 1 回、120〜150 ms の停止が発生した（p95 が 120〜150 ms）。\
独自のポストエフェクトでレンダーターゲットを生成する場合も、内蔵 GPU を対象にするなら `samples` を 0 にする。

### Bloom の Threshold

Bloom の Threshold は、トーンマッピング前の輝度と比較される。\
日の当たる白い面は輝度が 1 を超えるため、Threshold を 1 未満にすると、白い面全体がにじむ。\
発光させたい部分のみ、マテリアルの Emissive Intensity を上げて Threshold を超えさせる。
