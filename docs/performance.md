# 性能

THREE Stage のシーンを、目標のフレームレートとメモリの上限に収めるための文書。
読み手は、シーンを組む人と、プロジェクトのコード（コンポーネント、シェーダー、2D UI）を書く人。
設計上の目標、計測の方法、最適化の考え方、ポストプロセスの負荷の順に書く。

## 概要

THREE Stage のスタジオと、書き出したシーンを表示する組み込み先の Web アプリケーション（以下、組み込み先）は、同じランタイム（`@three-stage/runtime`）で描画する。
描画は WebGL2（three.js の WebGLRenderer）で、React Three Fiber の上で動く。
そのため、スタジオと、組み込み先と同じ描画だけを表示するページ（`preview.html`）で測った数字は、組み込み先でも同じ条件なら同じになる。

性能は次の順で扱う。

1. 設計上の目標を知る。フレームレート、対象とする PC、1フレームの時間の上限、メモリの上限。
2. スタジオの Stats と Profiler で、作りながら数字を見る。
3. `three-stage measure` と `three-stage soak` で、条件を揃えて測る。
4. 上限を超えたら、最適化の考え方に沿って減らす。

## 設計上の目標

ここに書く数字は、THREE Stage の設計上の目標である。
Stats と Profiler が色を変える上限と線、`three-stage measure` で比べる上限、`three-stage soak` の判定は、この目標を条件にしている。
組み込み先の PC と表示の条件がこれと違うときは、その PC で測って判断する。

### フレームレート

フレームレートの目標は 30fps で、60fps は目指さない。
性能の計測と上限の数字は、30fps を条件にする。

ランタイムは requestAnimationFrame（rAF）のたびに前の描画からの時間を見て、25ms 経っていなければ描画を飛ばす。
60Hz のモニターでは2回に1回描画するので、フレームの間隔が 33.3ms に揃う。
60Hz 以外のモニターでは、間隔が揃わない。

30fps の制限は、次の場所で切り替える。

| 場所 | 設定 |
|---|---|
| スタジオ | Viewport の上の Render の Frame Rate（`30 fps` か `Unlimited`） |
| `preview.html` | クエリの `limit=0` で制限を外す |
| 組み込み先 | `StageView` の `settings.limitFps`（既定は `true`） |

### 対象とする PC の区分

対象とする PC は、内蔵 GPU の仕様で区分する。

| 区分 | PC | メモリ | 描画 | 目標 |
|---|---|---|---|---|
| 推奨 | 一般的なデスクトップ PC の内蔵 GPU。Core i5 第12〜14世代（UHD 730 以上）、または Core Ultra | 16GB（8GB×2 のデュアルチャネル） | 1080p でレンダリングし、4K モニターにアップスケールする | 30fps |
| 最低 | Windows 11 が動く PC。Core 第8〜11世代の UHD 620/630、または N100/N150 のミニ PC | 8GB 以上 | Dynamic Resolution でレンダリング解像度を 720p まで下げる | 30fps |
| 対象外 | ブラウザが GPU を使えない環境。型番の末尾に F が付く Core（i5-12400F など）は内蔵 GPU が無いので、この区分になる | | | |

推奨の区分は UHD 730 を基準にする。
デスクトップ PC に多い i5-12400／13400／14400 の内蔵 GPU は UHD 730（24EU）で、UHD 770（32EU）が載るのは i5-12500 以上である。

Dynamic Resolution は、レンダリング解像度の設定（Resolution）が `auto` のときだけ働く。
既定は `1080p` なので、最低の区分の PC に向けるときは、組み込み先で `StageView` の `settings.resolution` を `auto` にする。
下げる条件は、下の「GPU」の表にある。

2D UI は HTML で、画面の解像度のまま描画する（4K のモニターなら 4K）。

### 1フレームの上限

基準にする PC は Core i5-1235U（Intel Iris Xe 80EU、最大 1.2GHz）である。
対象とする PC での時間は、内蔵 GPU の性能を基準の PC の Iris Xe との比で見積もり、基準の PC での1フレームの時間に直す。

| GPU | EU 数 × 最大クロック | 性能比（基準の PC を 1） |
|---|---|---|
| 基準の PC の Iris Xe（i5-1235U） | 80 × 1.2GHz | 1 |
| UHD 770（i5-12500 以上） | 32 × 1.45GHz | 0.48 |
| UHD 730（i5-12400／13400／14400） | 24 × 1.45GHz | 0.36 |
| UHD 620/630 | 24 × 1.0〜1.2GHz | 0.25〜0.30 |
| N150 | 24 × 1.0GHz | 0.25 |
| N100 | 24 × 0.75GHz | 0.19 |

性能比は、公称の EU 数とクロックから求めた理論値で、実測ではない。
メモリ帯域を含めていないので、画素の量で処理が詰まる場面では、実際の比と異なることがある。
Core Ultra は型番によって内蔵 GPU の構成が大きく異なるので、この表には含めない。

| 区分 | 対象とする PC での目標 | 計算 | 基準の PC での上限 |
|---|---|---|---|
| 推奨 | UHD 730 で 1080p 30fps（33.3ms） | 33.3 × 0.36 | 1080p で 12ms |
| 最低 | N100 で 720p 30fps（33.3ms） | 33.3 × 0.19 | 720p で 6ms |

この上限と比べるのは、30fps の制限を外して測ったフレームの間隔である。
Stats と Profiler は、描画バッファの高さが 760px 以下なら 6ms、それより大きければ 12ms を上限にする。
`three-stage measure` では、出力の `frameMs`（フレームの間隔の中央値）を比べる。

### メモリの上限

内蔵 GPU はメインメモリを共有する。
Intel は、Iris Xe の性能にはデュアルチャネルのメモリが必要としている。
メモリが1枚挿しだと、Iris Xe は UHD 相当の性能で動く。

| 項目 | 上限 |
|---|---|
| GPU 側のテクスチャ | 256MB |
| タブ全体 | 1GB |
| 長時間動かしたとき | 増え続けないこと |

Stats と Profiler は、JS のヒープが 1024MB を超えたら色を変える。
テクスチャは数（Textures）だけを表示するので、量は下の「GC とメモリ」の式で見積もる。
増え続けないかは、`three-stage soak` で確認する。

## 計測の方法

### Stats と Profiler

スタジオでは、作りながら2か所で数字を見る。
画面と項目の詳細は [studio.md の「Stats と Profiler」](studio.md#stats-と-profiler) にある。

| 場所 | 内容 |
|---|---|
| Stats（Viewport の右上） | fps とフレーム時間、CPU と GPU の時間、Calls、Triangles、Geometries、Textures、JS Heap、GC Alloc。上限を超えた値は色を変える |
| Profiler（下のタブ） | 項目ごとの直近60秒のグラフ。Frame Time と CPU・GPU には上限の線を、Frame Time には 33.3ms の線も引く |

30fps の制限があると、フレームの間隔は 33.3ms に揃い、重さが見えない。
重さを見るときは、Render の Frame Rate を `Unlimited` にする。
Stats がフレーム時間の色を変えるのは、`Unlimited` のときだけである。

### 計測の命令

条件を揃えて測るときは、`three-stage` の3つの命令を使う。
どれも、ウィンドウを開かずに起動したスタジオのサーバー（`three-stage <folder> --no-open --port 5180`）のページを、ヘッドレス Chrome で開く。
測る対象は、組み込み先と同じ描画だけを表示するページ（`http://127.0.0.1:5180/preview.html`）である。

| 命令 | 内容 |
|---|---|
| `three-stage shot <steps.json> <出力フォルダ>` | 1920×1080 のスクリーンショットを撮り、2D UI の文字の重なりとはみ出しを数える。見た目の確認用で、速さは測れない |
| `three-stage measure <URL か runs.json>` | 1フレームの draw call、ポリゴン数、パスごとの内訳、フレームの間隔を出力する |
| `three-stage soak <URL> --minutes <分>` | 長く動かして、JS のヒープと WebGL のオブジェクトの数が増え続けないかを判定する |

1フレームの上限と比べるときは、30fps の制限を外して測る。

```powershell
three-stage measure "http://127.0.0.1:5180/preview.html?limit=0"
```

長時間の安定は、モックデータの時刻を早送りして確認する（`speed=1440` で、モックデータの1日が1分で進む）。

```powershell
three-stage soak "http://127.0.0.1:5180/preview.html?start=00:00&speed=1440&limit=0" --minutes 30
```

引数、`preview.html` のクエリ、出力の項目は [packages/studio/tools/README.md](../packages/studio/tools/README.md) にある。

CPU の内訳を見るときは、Chrome の DevTools の Performance で、1フレームのうち Scripting と Rendering がどれだけかを見る。

## 最適化の考え方

最適化は4つに分けて考える。

1. 毎フレームの CPU の仕事を減らす。
2. 長く動かしても増えるものを無くす。
3. GPU が塗る画素を減らす。
4. 2D UI を軽く保つ。

内蔵 GPU では、ポリゴン数より画素の量が効くことが多い。
ブラウザでは CPU や GPU の使用率を直接指定できないので、1秒に描画する回数と、1回に渡す仕事の量で調整する。

### CPU

| 手法 | 内容 |
|---|---|
| フレームレートの制限 | 30fps にすると、CPU も GPU も仕事がおおよそ半分になる |
| 計算はデータの受信時にまとめる | データの更新はフレームよりずっと間隔が長い。並べ替えや配分は受信時に一度だけ計算し、毎フレームは補間だけにする |
| 動きはシェーダーに任せる | 流れや点滅は `uTime` などの uniform を1つ渡し、頂点ごとの動きは GPU で計算する |
| 動かないオブジェクトの行列を止める | 静的なオブジェクトは `matrixAutoUpdate = false` にする |
| 変わった部分だけ GPU に送る | `needsUpdate` は値が変わったときだけ立て、バッファは `addUpdateRange` で一部だけ送る |
| 切り替えのたびに作り直さない | 切り替えて見せるオブジェクトは保持したまま、表示と非表示だけを切り替える。最初に `renderer.compileAsync` でシェーダーを作っておく |

### スレッド

JavaScript のメインスレッドは1本で、JS、DOM の更新、three.js が描画命令を作る処理をすべて受け持つ。
GPU の処理は Chrome が別のプロセスで動かすので、描画のためにスレッドを分ける必要はない。

| 手段 | できること | THREE Stage での扱い |
|---|---|---|
| Web Worker | 重い計算を別のスレッドで動かす | 圧縮した glb（Draco）と KTX2 のテクスチャのデコードは、three.js のローダーが Worker で行う。コンポーネントの重い計算は、Worker に移せる |
| OffscreenCanvas | three.js の描画ごと Worker に移し、DOM と描画を分ける | ランタイムはメインスレッドで描画する |
| SharedArrayBuffer | スレッド間でメモリを共有する | 組み込み先のページに COOP と COEP のヘッダーが必要になる。ランタイムは使わないので、組み込み先にこのヘッダーは必要ない |

### GC とメモリ

GC（ガベージコレクション）は、どこからも参照されなくなったオブジェクトを、ブラウザが自動で解放する仕組みである。
解放の間は JS が止まるので、毎フレームオブジェクトを作ると、フレームが引っかかる。
GPU に載せたデータは GC の対象外で、`dispose()` で明示的に解放する。

| 対象 | 起きること | 手法 |
|---|---|---|
| JS の一時オブジェクト | 毎フレームの `new Vector3()`、配列、文字列が GC を呼ぶ | 一時変数は使い回す |
| 文字の更新 | 数値の整形で、毎フレーム文字列ができる | 表示が変わったときだけ書き換える |
| GPU のメモリ | ジオメトリ、マテリアル、テクスチャ、レンダーターゲットが残る | 不要になったら `dispose()` し、`renderer.info.memory` が増え続けないかを見る |
| 伸びる配列 | ログや時系列が、長く動かすと膨らむ | 長さを固定したリングバッファにする |
| DOM | 一覧に行を追加し続けると、削除し忘れた要素が残る | 行は一定の数だけ作り、内容だけを入れ替える |
| テクスチャの量 | 1枚が 幅×高さ×4バイト×1.33（ミップマップの分） | KTX2 は GPU の上でも圧縮したまま載るので、4〜8 分の1になる |

GC Alloc（Stats と Profiler）は、GC と GC の間に JS のヒープが1秒あたりどれだけ増えたかである。
毎フレームのオブジェクトの生成を減らすと、この値が下がる。

長時間で増え続けないかは、`three-stage soak` で見る。
手で見るときは、DevTools でヒープスナップショットを時間を空けて2回撮って比べる。

### GPU

| 手法 | 内容 |
|---|---|
| レンダリング解像度 | 効果がいちばん大きい。3D は 1080p か 720p で描画し、2D UI だけ画面の解像度で描画する。ランタイムは、Resolution の設定と Quality の Max Resolution の小さい方の高さで描画し、画面の画素より細かくは描画しない |
| Dynamic Resolution | Resolution が `auto` のとき、直近60フレームのうち12フレームを超えて、フレームの間隔が Frame Time Threshold（既定 40ms）を超えたら、高さを Minimum Resolution（既定 720）に下げる。判定は2秒に1回で、下げた後は戻さない。値は Render Settings で変える |
| ポストプロセス | 全画面のパスは1枚ごとに重い。負荷は下の「ポストプロセスの負荷」にある |
| シャドウ | 太陽のように光がゆっくり動くだけなら、`shadowMap.autoUpdate = false` にして、1分に1回などの間隔で更新する。影を落とすオブジェクトが動いたときは、その時点で `shadowMap.needsUpdate = true` にする。静的なオブジェクトの影は、モデルを作るツールでライトマップにベイクする。Quality の Shadow Map Scale で、シャドウマップの大きさを下げられる |
| 空の切り替え | Environment の HDRI と HDRI B を Blend で混ぜるとき、ランタイムは Blend を 64 段階に分け、段階が変わったときだけ環境光（PMREM）を作り直す。Blend が 0 と 1 の環境光は一度作ったら保持するので、作り直しは Blend が中間の値を通る間だけ起きる |
| リフレクション | Reflection Probe は毎フレームは撮り直さない。オブジェクトの追加と削除、シーンの定義の変更、表示と非表示の変更、空の切り替えのときだけ撮り直す（0.5秒に1回まで）。6面を1フレームに1面ずつ撮り、影は撮る時点のシャドウマップを使う。動き続けるオブジェクトは、撮り直すまで反射に反映されない |
| ライトの数 | ライトを増やすと、1画素ごとの計算が増える。エミッションとベイクで置き換え、ライトは2〜3個に抑える |
| オーバードロー | 半透明の大きな板や、加算で重なる光は、同じ画素を何度も塗る |
| 品質の段階 | Quality の High と Low で、レンダリング解像度の上限とシャドウマップの大きさを切り替える。組み込み先では `StageView` の `settings.quality` で選ぶ |

`powerPreference` は、GPU を2つ搭載したノート PC でしか効かない。

### 2D UI

2D UI は HTML で、画面の解像度のまま描画するので、4K のモニターでは描画する画素が多い。

| 手法 | 内容 |
|---|---|
| アニメーション | `transform` と `opacity` だけで動かす。幅や位置を変えると、レイアウトの計算が走る |
| 重い効果 | `backdrop-filter` のぼかしは 4K では重いので、使うなら測ってから使う |
| 範囲を区切る | パネルに `contain: layout paint` を付ける |

### パーティクル

1. 粒を1つずつ Mesh にせず、`InstancedMesh` か `Points` にまとめて、draw call を1回にする。
2. 位置は「経路上の位置 = fract(粒ごとの乱数 + 位相)」のように頂点シェーダーで計算し、CPU は uniform を渡すだけにする。
3. データの値に比例して速さを変えるなら、CPU で `位相 += 速さ × 経過時間` を積算してから渡す。時間に速さを直接かけると、速さが変わった瞬間に粒の位置が跳ぶ。
4. 最大数を最初に確保し、見せる数は `mesh.count` や `setDrawRange` で変える。
5. 粒は小さくして `depthWrite: false` にし、加算で重ねる数に上限を設ける。重なりすぎると、画面が白く飛ぶ。
6. 線に沿った流れは、帯状のメッシュの UV をずらす表現にすると、パーティクルより軽い。

ランタイムは WebGL2 で描画するので、コンピュートシェーダーは使えない。
粒どうしの当たり判定のようなシミュレーションは、粒の数を抑えて CPU か頂点シェーダーで計算する。

## ポストプロセスの負荷

ランタイムのポストプロセスは、three.js の EffectComposer で組む。
シーンを半精度の浮動小数のレンダーターゲットに描き、Bloom、トーンマッピングと sRGB への変換、FXAA、SMAA の順にかける。
プロジェクトが登録したポストエフェクトは、`stage` が `hdr` なら Bloom の後、`display` なら sRGB への変換の後に入り、1つごとに全画面のパスが1枚増える。
Vignette はトーンマッピングのパスの中でかけるので、全画面のパスは増えない。
有効なエフェクトが1つも無ければ、EffectComposer を使わず、キャンバスに直接描画する。

次の表は、2026-10-25 に、基準の PC（Iris Xe、D3D11）で、glb のモデルを十数個並べたシーンの `preview.html?limit=0` を `three-stage measure` で測った `frameMs`（中央値）である。

| ポストプロセス | 1080p | 720p |
|---|---|---|
| なし | 4.1ms | 3.2ms |
| Vignette | 5.6ms | |
| Bloom と Vignette | 8.5ms | |
| Bloom と Vignette と FXAA | 10.1ms | 5.3ms |
| Bloom と Vignette と SMAA | 14.0ms | |

SMAA を使うと、1080p の上限 12ms に収まらない。
アンチエイリアスが必要なら FXAA を使う。

ポストプロセスを使うと、キャンバスの `antialias`（MSAA）は最後のパスにしか効かないので、オブジェクトの縁がギザギザになる。
その代わりが FXAA である。
ランタイムのレンダーターゲットは MSAA を使わない。
同じ条件でレンダーターゲットに MSAA（`samples` を 2 か 4）を付けると、中央値は変わらないが、数フレームに1回 120〜150ms 止まった（p95 が 120〜150ms）。
自前のポストエフェクトでレンダーターゲットを作るときも、内蔵 GPU に向けるなら `samples` を 0 にする。

Bloom の Threshold は、トーンマッピングの前の明るさと比べる。
日の当たる白い面は 1 を超えるので、Threshold を 1 より下げると、白い面が全部にじむ。
光らせたい部分だけ、マテリアルの Emissive Intensity を上げて Threshold を超えさせる。
